Laboratorio Práctico

LAB: FILE PATH TRAVERSAL SIMPLE CASE

Informe técnico sobre la explotación de la vulnerabilidad de salto de directorio (Path Traversal / Directory Traversal), recuperando el archivo sensible /etc/passwd mediante la manipulación del parámetro filename en la carga de imágenes.

01

Ficha del laboratorio

Laboratorio: LAB: FILE PATH TRAVERSAL SIMPLE CASE
Nivel: Apprentice
Tipo de explotación: File Path Traversal (Directory Traversal)

02

Objetivo del laboratorio

Recuperar y visualizar el contenido del archivo sensible /etc/passwd del sistema operativo mediante la manipulación del parámetro filename en la funcionalidad de carga de imágenes.

03

Explicación técnica de la vulnerabilidad

La vulnerabilidad de salto de directorio (Path Traversal o Directory Traversal) se origina en una validación deficiente o nula de las entradas provistas por el usuario antes de ser procesadas directamente por las interfaces de programación de aplicaciones (APIs) del sistema de archivos del servidor. En una implementación segura, las peticiones de recursos estáticos deben resolverse dentro de un directorio base confinado (sandboxed). Sin embargo, cuando el backend concatena de forma directa el parámetro de entrada con una ruta estática en el almacenamiento local sin sanear secuencias de control de rutas, el sistema operativo interpreta secuencias como '../' como instrucciones de navegación relativa para retroceder un nivel hacia el directorio padre en el árbol de carpetas.

En el marco de OWASP Top 10:2021, esta debilidad se clasifica formalmente bajo la categoría A01:2021 - Broken Access Control (Control de Acceso Roto). Al evaluar la triada CIA, el impacto principal e inmediato recae sobre la Confidencialidad, dado que permite la exfiltración arbitraria de archivos del sistema operativo, configuraciones, credenciales y código fuente. No obstante, si la aplicación permite además operaciones de escritura sobre rutas manipuladas, la Integridad y la Disponibilidad se ven críticamente comprometidas.

El riesgo real en un entorno corporativo o productivo es severo: un atacante puede extraer archivos como /etc/passwd o /etc/shadow para obtener listas de usuarios y hashes de contraseñas, descubrir secretos de infraestructura en archivos .env o ficheros de configuración de bases de datos, y en escenarios avanzados donde concurre la subida de archivos o la sobreescritura de binarios/crons, evolucionar hacia una Ejecución Remota de Código (RCE) que resulte en la toma de control total del servidor.

04

Procedimiento paso a paso

  • Se inició el entorno de auditoría abriendo Burp Suite Community Edition y asegurando la configuración adecuada del proxy integrado para registrar el tráfico generado entre el navegador y la aplicación web vulnerable.
  • Se navegó a la página principal de la tienda en línea provista por el laboratorio, la cual despliega un catálogo de productos con sus respectivas imágenes ilustrativas, verificando que el reto se encontraba en estado 'Not solved'.
  • Al monitorear las peticiones generadas automáticamente por el navegador durante el renderizado de la página, se identificaron múltiples solicitudes HTTP concurrentes dirigidas al endpoint '/image', las cuales pasaban el nombre del recurso gráfico a través del parámetro 'filename' (por ejemplo, filename=7.jpg).
  • Se analizó el historial HTTP en la pestaña Proxy de Burp Suite, seleccionando una de las peticiones representativas que interactuaban con dicho endpoint para evaluar la mecánica de recuperación de archivos en el backend.
  • Mediante el menú contextual, se envió la petición seleccionada al módulo Repeater de Burp Suite con el atajo de teclado Ctrl+R, con el fin de iniciar las pruebas de manipulación de parámetros de forma aislada y controlada.
  • En Repeater, se ejecutó una primera prueba enviando una ruta absoluta directa (/etc/passwd) en el parámetro 'filename'. El servidor web respondió con un código 'HTTP/2 400 Bad Request' y el mensaje JSON 'No such file', lo que confirmó que el backend añade la entrada a un directorio base predefinido (tal como /var/www/images/) en lugar de ejecutar la consulta desde la raíz absoluta del sistema.
  • Identificado el comportamiento relativo, se procedió a inyectar una secuencia de escape de directorios conformada por retrocesos relativos sucesivos ('../../../etc/passwd') para salir del directorio de imágenes y alcanzar la raíz del sistema de archivos.
  • Al emitir la solicitud con la carga útil estructurada, el servidor respondió con un código 'HTTP/2 200 OK' y el encabezado Content-Type: image/jpeg, retornando en el cuerpo del mensaje el contenido en texto plano del archivo '/etc/passwd' del sistema operativo Linux.
  • Finalmente, tras completarse con éxito la lectura no autorizada del archivo del sistema, la plataforma de PortSwigger detectó la exfiltración y actualizó el estado del laboratorio a 'Solved'.

07

Explicación del payload

El vector de ataque utilizado es: '../../../etc/passwd' (o su variante extendida '../../../../etc/passwd').

Análisis sintáctico y funcional:

  • 1. '../': Representa la directiva estándar POSIX y de sistemas tipo UNIX para referenciar al directorio padre del directorio de trabajo actual. Cada repetición de esta secuencia retrocede un nivel en el árbol del sistema de archivos.
  • 2. Concatenación de secuencias: Al enviar tres o cuatro repeticiones ('../../../'), el puntero de ruta retrocede desde el subdirectorio de almacenamiento (por ejemplo, '/var/www/images/') hacia '/var/www/', luego hacia '/var/', y finalmente hacia la raíz del sistema '/'. En entornos UNIX, emitir secuencias de retroceso adicionales una vez alcanzada la raíz no produce error ni afecta el destino, manteniéndose siempre en '/'.
  • 3. 'etc/passwd': Especifica la ruta relativa que, a partir del directorio raíz ya alcanzado, conduce al archivo estándar del sistema donde se definen las cuentas de usuario, sus identificadores (UID/GID), directorios de inicio (home) y shells por defecto.

Al no existir sanitización ni validación contra listas blancas, la función del backend concatena la entrada de forma cruda (ej. '/var/www/images/' + '../../../etc/passwd'), resolviendo la ruta canónica en '/etc/passwd' y forzando a la API del sistema de archivos a leer y devolver un archivo sensible del sistema operativo.

08

Mitigación recomendada

Para mitigar eficazmente esta vulnerabilidad se debe implementar una estrategia de defensa en profundidad compuesta por los siguientes controles técnicos:

  • 1. Eliminación del paso directo de entradas a APIs del sistema de archivos: La solución más robusta consiste en evitar que el usuario manipule nombres o rutas de archivos. Se recomienda asociar cada recurso a un identificador único seguro (como un UUID o clave primaria numérica) almacenado en base de datos, resolviendo la ruta del archivo internamente sin intervención del cliente.
  • 2. Validación estricta por lista blanca: En caso de requerir el ingreso de nombres de archivo, validar que el valor contenga exclusivamente caracteres alfanuméricos simples y extensiones autorizadas predeterminadas, rechazando de tajo cualquier carácter separador de ruta ('/', '\') o secuencias de puntos.
  • 3. Canonicalización y verificación de ruta base: Antes de acceder a cualquier recurso, utilizar las funciones nativas del lenguaje o entorno para resolver la ruta absoluta canónica del archivo solicitado (por ejemplo, 'getCanonicalPath()' en Java o 'realpath()' en PHP) y verificar programáticamente que la ruta resultante comience estrictamente con la ruta del directorio base autorizado.
  • 4. Principio de menor privilegio: Asegurar que el proceso del servidor web o demonio de la aplicación se ejecute con una cuenta de servicio de privilegios mínimos (chroot / jail o contenedor aislado), restringiendo a nivel de permisos de sistema operativo la lectura sobre directorios críticos (/etc, /root, /var/log).
  • 5. Implementación de WAF y auditorías continuas: Desplegar un Web Application Firewall con firmas y reglas de inspección profunda capaces de bloquear patrones comunes de evasión de rutas, complementándolo con análisis estático de código (SAST) y pruebas de penetración periódicas.
