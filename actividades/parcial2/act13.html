Parcial 2 · Actividad 13

Red Team Report

Pentesting de My File Server 1

Ejercicio de prueba de penetración en entorno de caja negra sobre la máquina virtual My File Server: 1 (VulnHub), integrando fases de reconocimiento, enumeración de servicios, explotación de configuraciones débiles y escalada de privilegios a nivel de kernel.

01

Executive Summary (Resumen Ejecutivo)

Como parte del ejercicio académico de la Actividad 13, se realizó un ejercicio de pentesting de caja negra sobre la máquina vulnerable "My File Server: 1", la cual simula un entorno corporativo dedicado a servicios de almacenamiento y archivos compartidos (FTP, SMB/NFS y un portal web informativo). El objetivo fue identificar, explotar y documentar las vulnerabilidades presentes, actuando como analista de Red Team contratado por la organización ficticia dueña del sistema.

El resultado del ejercicio fue un compromiso total del sistema (root), logrado en un tiempo relativamente corto y sin necesidad de herramientas de fuerza bruta. La cadena de ataque combinó fallas de configuración de servicios de archivos con una vulnerabilidad crítica del kernel Linux:

  • Acceso anónimo habilitado en los servicios FTP (puertos 21 y 2121) y SMB, incluyendo un recurso compartido (smbdata) con permisos de lectura y escritura sin autenticación.
  • Divulgación de información sensible: credenciales válidas (smbuser:rootroot1) se encontraron en texto plano dentro de un archivo público del servidor web (/readme.txt).
  • Uso de las credenciales obtenidas para escribir una clave pública SSH como authorized_keys del usuario smbuser, logrando así acceso remoto interactivo persistente sin necesidad de contraseña.
  • Escalada de privilegios a root explotando CVE-2016-5195 (DirtyCOW), una vulnerabilidad de condición de carrera en el subsistema de memoria del kernel Linux 3.10, confirmada mediante la obtención del archivo /root/proof.txt.

El nivel de riesgo global del sistema se clasifica como CRÍTICO. La combinación de servicios mal configurados, ausencia de control de acceso y un kernel obsoleto sin parchear permite a cualquier atacante no autenticado en la red obtener control total del servidor en pocos pasos. Se recomienda remediación inmediata siguiendo las acciones descritas en la sección 9 de este informe, priorizando la actualización del kernel, la deshabilitación de accesos anónimos y la eliminación de credenciales expuestas.

Evaluar el nivel de exposición y el riesgo de seguridad de la máquina "My File Server: 1" mediante una metodología estructurada de pruebas de penetración, documentando hallazgos técnicos, evidencia, análisis de impacto y recomendaciones de remediación.

03

Metodología Aplicada

El ejercicio se desarrolló siguiendo una adaptación de las fases del PTES (Penetration Testing Execution Standard), en línea con los lineamientos de la asignatura. Las fases aplicadas fueron:

  • Reconocimiento: identificación del objetivo activo en la red mediante descubrimiento de host.
  • Enumeración: identificación de puertos, servicios, versiones y recursos compartidos expuestos.
  • Explotación: obtención de acceso inicial aprovechando configuraciones débiles y credenciales expuestas.
  • Escalada de privilegios: elevación de un usuario estándar a root mediante una vulnerabilidad del kernel.
  • Post-explotación: confirmación del compromiso total del sistema.
  • Análisis y reporte: evaluación de impacto (modelo CIA) y elaboración de recomendaciones.

04

Fases de Reconocimiento

El primer paso consistió en identificar la dirección IP de la máquina víctima dentro del segmento de red Host-Only compartido con la máquina atacante (Kali Linux), utilizando la herramienta netdiscover para realizar un barrido ARP.

La dirección IP 192.168.56.104 se identificó como la máquina víctima (el vendor MAC "PCS Systemtechnik GmbH" corresponde a VirtualBox), quedando establecida como el objetivo para el resto del ejercicio.

05

Enumeración

5.1 Escaneo de puertos y servicios

Se ejecutó un escaneo completo de puertos (-p-) con detección de versión (-sV) sobre los 65,535 puertos TCP, con el fin de identificar todos los servicios expuestos, incluyendo aquellos en puertos no estándar.

El banner de Apache confirmó que el sistema operativo base es CentOS. Esta pista, junto con la antigüedad de las versiones de servicio detectadas, permitió anticipar que el kernel subyacente podría ser vulnerable a fallas de escalada de privilegios conocidas, hipótesis confirmada posteriormente en la sección 7.

5.2 Escaneo agresivo (nmap -A)

Se complementó el escaneo anterior con un análisis agresivo (-A), que combina detección de sistema operativo, versión de servicios y scripts de enumeración NSE, para obtener detalle adicional de cada servicio.

  • Hallazgo H-01 / H-02 — FTP anónimo habilitado (puertos 21 y 2121): El script ftp-anon de Nmap confirmó que el servicio FTP del puerto 21 (vsftpd) permite inicio de sesión anónimo (código FTP 230), y que el directorio pub se reportó como writeable (permisos 777, drwxrwxrwx), lo que habilita la escritura de archivos arbitrarios sin autenticación. El mismo escaneo identificó un segundo servicio FTP (ProFTPD) en el puerto 2121, también con acceso anónimo habilitado.
  • Hallazgo H-03 — SMB con firma de mensajes deshabilitada: El script smb-security-mode reportó message_signing: disabled (dangerous, but default), exponiendo el servicio a ataques de tipo SMB relay.
  • Hallazgo H-04 — Método HTTP TRACE habilitado: El servicio web permite el método HTTP TRACE, lo cual puede facilitar ataques de Cross-Site Tracing (XST) en combinación con vulnerabilidades del lado del cliente.

5.3 Prueba de conexión FTP

Adicionalmente a la detección automática de login anónimo reportada por Nmap, se realizó una prueba de conexión directa a ambos servicios FTP (puertos 21 y 2121), utilizando un nombre de usuario de prueba sin privilegios (alfredo). El objetivo de esta prueba fue únicamente verificar el comportamiento de autenticación de ambos servicios ante credenciales no válidas.

En ambos casos la conexión fue rechazada, confirmando que el acceso sin autenticación documentado en los hallazgos H-01 y H-02 depende específicamente del usuario reservado anonymous (tal como lo identificó el script ftp-anon de Nmap), y no de una falla generalizada de validación de credenciales en el servicio.

5.4 Enumeración de servicios SMB

Se enumeraron los recursos compartidos de Samba utilizando una sesión sin credenciales (sesión nula), tanto para listar los shares disponibles como para verificar los permisos efectivos sobre cada uno.

Hallazgo H-05 — Sesión nula SMB con recurso compartido de escritura anónima: Con una sesión NULL (sin credenciales) se obtuvo acceso de lectura y escritura completo (READ, WRITE) sobre el recurso compartido smbdata. El recurso smbuser, en cambio, no permitió acceso anónimo (NO ACCESS), lo que sugería la existencia de credenciales específicas para dicho usuario, confirmadas en la siguiente sección.

5.5 Enumeración de directorios del servicio web

Se ejecutó Nikto contra el servicio HTTP en el puerto 80, identificando un archivo de nombre readme.txt accesible públicamente y potencialmente interesante.

Al acceder al archivo desde el navegador, se confirmó el contenido revelando una credencial en texto plano:

Hallazgo H-06 — Credenciales en texto plano expuestas vía HTTP (Crítico): El archivo reveló la credencial smbuser: rootroot1, correspondiente al usuario que en la sección anterior no tenía acceso anónimo al recurso SMB smbuser. Esta única falla de configuración compromete la confidencialidad del sistema, ya que dicha credencial resultó válida para el servicio FTP y sirvió como base para el acceso inicial descrito en la siguiente sección.

06

Explotación

Con la credencial smbuser: rootroot1 obtenida en la fase de enumeración, se procedió a establecer un mecanismo de acceso remoto persistente mediante la inyección de una llave pública SSH en el directorio del usuario, aprovechando el acceso de escritura otorgado por el propio servicio FTP al autenticarse con credenciales válidas.

6.1 Generación del par de llaves SSH

Se generó un par de llaves SSH (tipo ED25519) sin frase de contraseña en la máquina atacante (Kali Linux), con el fin de automatizar el acceso remoto sin depender de contraseñas:

6.2 Carga de la llave pública como authorized_keys

Se inició sesión FTP utilizando la credencial smbuser: rootroot1 (en lugar de la sesión anónima), lo que otorgó acceso de escritura sobre el propio directorio home (/home/smbuser).

6.3 Acceso remoto mediante autenticación por llave

Con la llave pública instalada como authorized_keys, se estableció una conexión SSH utilizando la llave privada correspondiente, logrando acceso interactivo sin necesidad de contraseña:

Hallazgo H-07 — Acceso inicial mediante inyección de llave SSH (Alto): La combinación de (a) una credencial válida obtenida por divulgación de información y (b) permisos de escritura del propio usuario sobre su directorio .ssh vía FTP, permitió establecer un mecanismo de acceso remoto persistente e interactivo sin depender nuevamente de la contraseña original. Este es el punto de acceso inicial (foothold) sobre el sistema operativo de la víctima.

07

Escalada de Privilegios

7.1 Identificación de la versión del kernel

Una vez dentro del sistema con el usuario smbuser, se verificó la versión del kernel para identificar posibles vulnerabilidades de escalada de privilegios conocidas:

La versión 3.10.0-229.el7 (CentOS 7, compilada en 2015) corresponde a un kernel desactualizado y vulnerable a CVE-2016-5195, conocida como DirtyCOW.

7.2 CVE-2016-5195 - DirtyCOW

DirtyCOW es una vulnerabilidad de escalada de privilegios en el kernel de Linux que permite a un usuario local sin privilegios obtener acceso de escritura sobre asignaciones de memoria de solo lectura, explotando una condición de carrera (race condition) en la forma en que el subsistema de memoria maneja la ruptura de copy-on-write (COW) de mapeos de memoria privados de solo lectura. El exploit público utilizado (40616.c) aprovecha esta condición para sobrescribir un binario del sistema y obtener una shell con privilegios de root.

7.3 Transferencia y compilación del exploit

El código fuente del exploit se obtuvo del repositorio público de SecWiki (github.com/SecWiki/linux-kernel-exploits) y se transfirió a la víctima levantando un servidor HTTP temporal en la máquina atacante:

7.4 Confirmación del compromiso total (root)

Tras la ejecución del binario compilado, el propio exploit reporta su progreso (copia de respaldo del binario objetivo, condición de carrera y sobreescritura) y culmina entregando una shell con privilegios de root, confirmada al leer el archivo /root/proof.txt:

Hallazgo H-08 (enumerado como H-09 en texto original) — Escalada de privilegios vía DirtyCOW / CVE-2016-5195 (Crítico): La explotación exitosa de DirtyCOW confirma que el sistema operativo de la víctima no cuenta con los parches de seguridad correspondientes. Esto representa el hallazgo de mayor criticidad del ejercicio, ya que otorga control total (root) sobre el sistema a partir de cualquier acceso local, por mínimo que este sea.

08

Análisis de Impacto (Modelo CIA)

DimensiónImpacto y Detalle
Confidencialidad Compromiso total. El atacante obtuvo acceso de lectura a la totalidad del sistema de archivos producto del acceso root final. Previamente ya se había filtrado información sensible (credenciales en texto plano).
Integridad Compromiso total. Con privilegios de root, el atacante puede modificar o eliminar cualquier archivo del sistema, incluyendo binarios del sistema operativo, páginas del sitio web, registros de auditoría o la configuración de los propios servicios (FTP, SMB, SSH), pudiendo incluso instalar mecanismos de persistencia adicionales o borrar evidencia de su actividad.
Disponibilidad Impacto alto (potencial). Si bien no se ejecutaron pruebas de denegación de servicio por estar fuera del alcance definido, el nivel de acceso obtenido (root) permite detener servicios críticos, eliminar datos de los recursos compartidos o incluso inutilizar por completo el servidor, afectando la continuidad operativa de la organización.

En conjunto, el sistema evaluado presenta un riesgo CRÍTICO: la cadena de explotación no requirió técnicas sofisticadas ni fuerza bruta, sino la combinación de configuraciones por defecto inseguras (acceso anónimo), higiene deficiente de credenciales (archivo de texto plano expuesto) y falta de gestión de parches.

09

Recomendaciones Técnicas

#Recomendación
1Deshabilitar las sesiones nulas (NULL session) en Samba y revisar los permisos efectivos de todos los recursos compartidos, eliminando la escritura anónima sobre smbdata.
2Forzar la firma de mensajes SMB (server signing = mandatory) para mitigar ataques de tipo SMB relay.
3Deshabilitar el método HTTP TRACE en la configuración de Apache (TraceEnable Off).
4Eliminar cualquier archivo de notas o configuración con credenciales en texto plano del directorio público del servidor web; adoptar un gestor de secretos o variables de entorno protegidas.
5Restringir los permisos de escritura de los usuarios de bajo privilegio sobre su propio directorio .ssh cuando se accede vía servicios de archivos (FTP/SMB), y monitorear cambios en archivos authorized_keys mediante herramientas de integridad de archivos (FIM).
6Actualizar el kernel del sistema operativo a una versión soportada y parchada; implementar un proceso formal y periódico de gestión de parches (patch management).
7Aplicar el principio de menor privilegio a cuentas de servicio como smbuser, limitando su alcance únicamente a los recursos estrictamente necesarios.
8Implementar monitoreo y alertamiento centralizado (SIEM) para detectar patrones anómalos como sesiones anónimas exitosas, transferencias de archivos inusuales o compilaciones de binarios en rutas temporales.

11

Conclusión

El ejercicio demostró que la máquina "My File Server: 1" presenta una superficie de ataque amplia y múltiples fallas de configuración de baja sofisticación (acceso anónimo, credenciales en texto plano) que, combinadas con la falta de actualización del kernel, permiten un compromiso completo del sistema en cuestión de horas y sin necesidad de herramientas avanzadas de explotación. Esto subraya la importancia de aplicar controles básicos de higiene de seguridad —deshabilitar accesos anónimos, no almacenar credenciales en texto plano y mantener los sistemas parchados— como primera línea de defensa, incluso antes de considerar controles más sofisticados.

Se recomienda a la organización priorizar las acciones descritas en la sección 9, comenzando por la actualización del kernel y la eliminación de las credenciales expuestas, dado que ambos hallazgos están directamente vinculados con los puntos de mayor criticidad de la cadena de ataque documentada.
